# 多模型协作通用规则

适用：一个人只对接一个对话入口，由它调度多个模型做增量式开发。
角色：**组长** = 正在和用户对话的模型；**大模型执行者** = 另一家订阅型模型（如 Codex/Claude）；**便宜执行者** = 按量计费的低价模型（如 DeepSeek）。各成员是谁、擅长什么、额度如何，见各自的 profile。

## 派不派：按轮数，不按行数
- 估自己做要几轮调用 N：把需求确认 / 实现 / 验证 / 修测试分开估再加总（实测普遍低估一倍）。
- **大脑只有一个**：组长负责理解需求、拍板方案；执行者只执行，不参与讨论。
- **方案已定、任务说得清的实现活（N≥3），默认交给大模型执行者**，不是"非必要不派"；N≤2 的小改自己做。组长留下与用户沟通、验证、git 等有外部副作用的操作。
- **派活检查点**：用户批准方案 / 说"开工"的那一刻——说明已现成，在这里按 N 决定。
- **长会话门槛**：组长会话已超约 80 次调用，后续实现活优先派出去，或建议用户开新会话（组长每次调用都要重读整段上下文，越长越贵）。
- **过程很长、只要结论的活派出去**：截图看效果、长日志、跑测试修到绿、跨仓库翻文件、批量机械改。组长对话越短，每一轮越便宜，注意力也越集中。
- **N≥3 仍自己做，必须在交代里写不派的理由**（如"需求还在边聊边定""只有组长能拿到的环境"），N≥4 时再用账本 `task note` 记一条。
- 日常派活直接用派发脚本，不需要用户显式调用 team-dev；team-dev 的锁 + 快照 + 验收全流程才需显式调用。

## 派活与验收
- 派活说明写完整：背景、约束、写入范围、验收标准、"不算完成"清单。
- **执行者只拿结论，不拿对话**：说明里单列"已定的决策"（每条一句结论 + 一句理由，包括否掉的方案），执行者不用知道是怎么聊出来的。
- 多方并行改同一目录时，派活前划清文件归属，不交叉写同一文件。
- 每件活做完给用户一行交代：怎么做的（自己 / 派给谁）、几轮、测试是否通过、哪里没把握。
- 派活脚本跑完自动做一次初筛（便宜判断模型看 diff），报警项附在结果里；初筛只是报警器，不判断改得对不对，没报警也要看 diff。
- 审查按风险分级：
  - low（文案、注释、单文件小改）= 自动检查 + 初筛 + 组长看 diff；
  - mid 及以上 = 再加一次**无上下文审查**：审查者不是实现者、不看对话，只拿任务说明 + diff + 只读仓库（实现者是 Codex → 新开的 Claude 审；否则 → Codex 审）；
  - high 另需开工前写定阻塞标准，审查只按它判通过 / 不通过。
- 同一问题修两次仍没解决，或用户说"还是不行"：停下来，把现象 + 已试方法交给另一家大模型用全新视角排查，不硬磨第三次。
- 互相派活时对方的产出认真对待、具体反馈，不甩锅不互相否定。

## 规则怎么调
- 改规则、阈值、提示词前后，用 `evals/` 里的固定测试集整套重跑对比，不临时找一两个例子试；测试集从真实任务里攒（Anthropic 做法：约 20 个真实样本起步）。

## 硬规则（代码强制）
- 敏感任务（鉴权 / 密码 / token / 密钥 / 支付等，或 risk=high）绝不下放便宜执行者。
- 便宜执行者最多 2 次，失败即升级给另一家大模型。
- 提交、推送、部署、发消息、改全局配置不外派，由组长在用户确认后亲自做。

## 成本可见
- 账本自动按会话统计调用数 / 折算金额 / 仓库，长会话标红；派活由派发脚本自动记账。
- 小活不记账；`task end` 窗口过短会被拒绝（防事后补记）。复盘靠查会话历史。

## 共享记忆
- 只有组长写记忆；被派活的一方不写。写前先查同主题，更新而非重复。
- 规则 / 偏好直接照做，稳定事实直接用；易变状态（进度、分支是否已推送）动手前用 git 确认，并尽量少记。
- 只记用户亲口说的或实际验证过的结论，易变状态注明日期；与代码 / 验证矛盾时以代码为准，当场修正。
